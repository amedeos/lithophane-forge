# AGENTS.md

Guidance for coding agents working in this repository.

## Project

`lithophane-forge` turns a photo into a printable colour picture or lithophane and a ready-to-print PrusaSlicer project. It follows the conventions of the owner's earlier project `/workspace/3d-linux` (uv, build123d, one CLI, a numpy renderer, PrusaSlicer CLI for projects).

- **Printer:** Prusa MK4 (Input Shaper firmware) with **one extruder**: no MMU. Colours come only from M600 colour changes by layer height. Other Prusa printers are in `printers.PRINTERS`.
- **Material:** **PETG** by default (`--material pla` for PLA). The thickness defaults in `optics.DEFAULTS` are estimates until the owner calibrates a spool.
- **Advice:** `image.analyse(..., colour=True)` gives advice for colour prints (no thickness claims, no `--clahe`, no warning about colourful photos); `make` passes the mode, `analyze` takes `--mode` (colour by default). `analyze --light` without `--colors`, or `--colors`/`--light` with `--mode mono`, are usage errors.
- **Modes:** colour is the **default** on the command line for flat and shaped panels (`job_from` picks it when `--mode` is not given; `Job` itself still defaults to mono, which the tests rely on). Mono (`--mode mono`, white filament): flat, curved and cylinder panels print **standing** (thickness along y or radial), shaped panels print **lying** (thickness along z); curved and cylinder are always mono. Colour: M600 changes, flat or shaped, printed **lying**. **Light:** a colour print is by default a picture seen in **room light, from the top** (`--light front`, `view="relief"`, not mirrored; `job_from` picks it, `Job` itself defaults to `light="back"` like the mode); `--light back` makes a colour lithophane, lit from behind (default `view="flat"`). Mono is always backlit. The owner asked for front light as the default on 2026-11-02, because they want to look at the print like a photo, with no lamp. The ideal colours come from the photo alone and only then are matched to real PETG (Prusa's published hex and TD values) or to `--filaments`. The colour analysis must not depend on the filaments the owner has; owned filaments come in only through that explicit option. In room light, translucent coloured or nearly clear filaments without measured `k` and `s` are left out of the real filaments unless `--allow-unmeasured` (hex and TD cannot predict them: the owner's first room-light print showed it).
- **License:** GPL-3.0-only.

## Environment and commands

- Python 3.14 (3.13 also works), [uv](https://docs.astral.sh/uv/), numpy, Pillow, scikit-image, build123d 0.13 (accessories, later), PrusaSlicer 2.9 (optional), ONNX Runtime 1.31 (optional extras `vision` for the CPU or `vision-gpu` for CUDA; uv refuses both together: `[tool.uv] conflicts`).

```sh
uv sync                           # add --extra vision for --focus subject
uv run pytest                     # ~120 s; -m "not slicer" skips the PrusaSlicer runs; -m vision needs the extra and the models
uv run ruff check . && uv run ruff format --check .
uv run lithophane-forge analyze PHOTO [--mode mono]   # advice for a colour print (or mono)
uv run lithophane-forge make PHOTO [--colors N] [--filaments FILE] [--width MM] [--slice]   # colour picture, room light, lying
uv run lithophane-forge make PHOTO --light back [--colors N] [--slice]   # colour lithophane, lit from behind
uv run lithophane-forge make PHOTO [--focus MASK.png|X,Y,W,H|centre|subject] [--focus-floor F] [--min-patch-subject MM2] [--smooth-background MM] [--device auto|cpu|gpu]   # colours and detail for the subject first
uv run lithophane-forge make PHOTO --mode mono [--shape flat|curved|cylinder] [--slice]   # white, standing
uv run lithophane-forge analyze PHOTO --colors N [--light back]
uv run lithophane-forge calibrate [--slice]
uv run lithophane-forge printers
uv run lithophane-forge models [--download]   # the models of --focus subject, their folder, the device
```

- Test photos go in `photos/` (git-ignored, only `.gitkeep` is tracked): the owner's personal photos never go into the repository.
- Output goes to `out/<name>/` (git-ignored). `forge.clear_outputs` first removes what an earlier run wrote there under the same name (only the kinds of file we write, never the photo), so no stale G-code stays next to a new project: `<name>.stl`, `<name>.3mf` (project), `<name>.bgcode` with `--slice`, `preview.png`, `plan.json`, `report.md`, `focus.png` with `--focus`. Everything there is an output: a focus map to edit goes next to the photo (the report says so); a `--focus out/<name>/focus.png` still works, because the mask is read before the folder is cleared and the same map is written again.
- `$LITHOPHANE_FORGE_MODELS` names the folder of the `--focus subject` models (default `$XDG_CACHE_HOME/lithophane-forge/models`, else `~/.cache/...`). They download on first use, through a temporary `.part` file of their own in that folder (two runs at once do not share one), checked by SHA-256 (`vision.fetch`; a network error, a folder that cannot be written and a hash mismatch are distinct `ValueError`s). The URLs are fixed (a Hugging Face commit, rembg's release assets). On use only the size is checked; `models` checks the hash and `models --download` replaces a damaged file.
- `$LITHOPHANE_FORGE_PROFILES` names the PrusaResearch.ini (or its folder) when it is not in `profiles.SEARCH` (system install, PrusaSlicer's data folder, Flatpak). `$PRUSA_SLICER` names the PrusaSlicer command; a value that names no command is a usage error, not "PrusaSlicer not found".

## How a lithophane is built

- **Light.** The photo's lightness (L*) gets levels, optional CLAHE and gamma, then becomes linear light. `Optics.thickness` maps light to thickness with Beer-Lambert between `t_min` (brightest) and `t_max` (darkest).
- **Grid.** Points are `pitch` apart (0.2 mm); the outer size is exact (`linspace`). Above `max_triangles` the pitch grows and a note says so. The frame (`frame` mm wide, `t_max + 0.8` thick) is part of the grid; the photo fills the inside.
- **Mesh.** `mesh.shell` joins the relief face (every grid point) and the flat face (only its edge points: long strips, and fans at the two end strips). About two triangles per grid point. Always closed, positive volume.
- **Overhangs.** A standing panel has ledges on the relief side where a thick part lies above a thin one. `forge.limit_overhangs` thickens the plastic below so that nothing leans out more than `max_overhang` (60° from vertical). PrusaSlicer's MK4 presets want support beyond 50°; the test slices with the threshold at our limit + 5° and expects no support.
- **Viewing side.** For lithophanes the flat face looks at the viewer by default and the light goes behind the relief. A colour picture in room light (`light="front"`) shows its top face (`view="relief"`; `Job.check` refuses `view="flat"` with it). The tests check that the picture reads the right way round from the viewer's side, for both views and every shape.
- **Shaped panels.** The grid cells whose centre lies inside the outline inset by half the frame width form the lithophane (`mesh.lying_masked`): its edge is stepped. The frame (build123d, the full frame width inside the outline) is a second volume of the same object and covers the steps; PrusaSlicer joins the two. Standing shaped panels would need support under the lower half of the outline, so they print lying.
- **Cylinder.** The grid wraps around (`mesh.arc(wrap=True)`); the frame is only at the top and bottom (rims). The middle of the picture faces −y, the seam is at the back. The default height is 1.25 × the diameter; `cylinder_notes` says how much of the photo is cropped and which `--repeat` fits it.
- **Accessories.** Stand (slot `frame_t + 2 × 0.10` mm, as deep as the frame) and lamp base (recess `diameter + 2 × 0.30` mm, LED pocket, cable notch) are separate 3MF projects with `layer_height = 0.2` as an object setting.

## How a colour print is chosen

- **Model, light from behind (`Backlight`).** A filament with linear colour c and transmission distance td has per-channel attenuation a = ln(10) / td × ln(c) / ln(Y(c)): a grey lets 10 % through at t = td on every channel, a coloured filament passes its own colour. A point of height h holds filament k between `starts[k]` and `starts[k+1]`; the light through it is exp(−Σ d_k a_k). The viewer's white is light through the thinnest stack of white PETG (td 3.4).
- **Model, light from the front (`Frontlight`).** Two-flux (Kubelka-Munk) per linear RGB channel: a filament has an absorption K per channel and one scattering S, in 1/mm, and the model uses a = 1 + K / S, b = sqrt(a² − 1). A layer d mm thick over a stack that reflects R_g shows (1 − R_g (a − b coth x)) / (a − R_g + b coth x) with x = b S d; `palette.reflect` writes it with e^−2x so that thick layers do not overflow (numpy warnings would reach the terminal). From the bed up each layer goes over the stack below it, starting from black behind the panel. A filament with measured `k` and `s` (`Filament.optics`) uses them; for the others (`two_flux`) the hex is the colour of a thick block (R_∞ = a − b, which gives K / S) and S is the one that lets `TD_THROUGH` (10 %, the project's definition of TD) of the luminance through td mm (a bisection on S × td for all filaments at once; Newton was no faster). Thin layers of a translucent filament are colour filters, not paint: 0.2 mm of Yellow Gold over white is a bright lemon, 0.1 mm of Ultramarine over that a dark green, and three layers of Signal White over black are still about L* 72. This model replaced a paint model (an sRGB blend with AutoForge's coverage sqrt(d / (0.1 td))) after the owner's first room-light print (Machu Picchu, 60 mm): the report promised a mean Delta E of 9.7, the print measured about 18 to 21, the grass printed lemon instead of khaki. `out/front-light-analysis.md` (git-ignored) has the measurements; a two-flux fit to them reached Delta E 3.5, and the tests `test_white_over_black_builds_up_slowly` and `test_the_failed_print_is_predicted` hold its main numbers. Hex and TD describe opaque filaments (TD ≤ `OPAQUE_TD`, 1 mm) and white or grey ones (chroma ≤ 12, TD ≤ `NEUTRAL_TD`, 4 mm) well enough, but not translucent coloured ones (Ultramarine has "TD 8" and absorbs red within 0.2 mm) or nearly clear ones (the model made 0.2 mm of V0 Natural, TD 10.4, a white veil that halved the chroma under it; its hex says little about its scattering): `predictable` says which, and `choices` leaves the others out in room light unless `allow_unmeasured`, with their names in the report's source line. The base must hide what is behind the panel: `hides_from` is the first layer top at which the filament looks the same (Delta E < `HIDE_DE` = 3) over black and over a white wall (0.8); `is_base` is true when that is the thinnest stack. At the default 0.6 mm only opaque filaments pass (blacks, greys, Jungle Green, Chalky Blue); Signal White needs about 1.8 mm. `base_td`, the bound of the ideal base's td, is the largest td at which Signal White's colour hides at the thinnest stack. The viewer's white is Signal White, thick (its luminance). A plan takes about 1.5 to 2 times as long as with the paint model, because Powell's cost is no longer flat and it does more steps (the suite went from about 100 s to 120 s).
- **First filament notes (`forge.base_notes`).** `choose` takes the base from the filaments that can be one (`is_base` of the light model) and falls back to any filament when the list has none: then a note says so (in room light: the wall shows through, with the `--t-min` at which the chosen base hides it, or that it never does; lit from behind: the base tints every point). There is no note asking for a light first filament in room light: a light filament hides the back only from about its TD, so the light colours come from light filaments over a dark base.
- **Fit.** `Fitter.cost` is the mean weighted CIELAB distance (lightness × 1.5) from 3000 sampled pixels to the path sampled at every layer top. `ideal()` moves the base (light from behind: grey level, td ≥ 2; light from the front: any colour, td up to `Frontlight.base_td`) and colour and td of the others, plus the change heights; it never returns something worse than its start. It never changes the order of the filaments, so `plan()` runs it from two k-means starts, lightest first, and with light from the front also darkest first. Its heights are free and can lose quality when they are snapped to layer tops; with the earlier paint model for room light it also stopped early, because the cost was flat for thick runs (on the owner's Machu Picchu photo the ideal was once worse than the print, 9.9 against 8.7). So `plan()` also runs `choose` on the photo's own colours (`photo_colours`: 8 k-means colours and 4 neutral greys, each at 0.5 and 1.5 × `ideal_td`), on layer tops, and refines that result with `ideal()`. The ideal is the best of all of them, compared with the changes on layer tops. The ideal colours depend on the photo alone (a test checks that two filament lists give the same ideal). Then `choose` picks the real filaments. It starts from the closest colours, with every change on a layer top. Then it takes one position at a time and tries every filament at every layer top between the changes below and above; it keeps the best pair and repeats until nothing changes. The changes never leave the layer tops, so every cost it compares is the cost of a plan that can print. (An earlier version chose filaments with the heights fixed and got stuck: a dark filament low in the stack hides every change above it. Another fitted the heights freely and then lost quality when they were snapped to layers.) `Fitter.costs` scores all candidates of a position in one pass, and the heights below the change under that position are computed once. The search for real filaments starts from the ideal colours and from the first two k-means starts (seeds 0 and 1 lit from behind, both orders of seed 0 in room light), and keeps the best. The real print is usually worse than the ideal, but nothing guarantees it. `kmeans_lab` asks scipy for no more clusters than the photo has colours and silences its warnings: they reached the terminal. `report.md` lists, for every ideal colour, the closest filament by colour alone.
- **Heights.** Changes sit on layer tops below the top layer; the M600 is at the top of the first layer of the new filament (`Fit.colour_changes`). `_on_layers` drops filaments that no point holds (a change snapped to the top layer, or two changes at one height), so a plan may use fewer filaments than `--colors`. `assign()` gives every pixel its height (same weighted distance), then a 3 × 3 median filter smooths the surface and `forge.remove_specks` (an area opening, then an area closing, from scikit-image) removes every island and hole smaller than `Job.min_patch` (`--min-patch`, 1 mm² by default) in every layer (with `--focus`, per region: see Focus): they print as blobs and show as specks (the owner's first room-light print had many). One pass is enough, because the closing only fills holes and makes no new island; a thin ring around a patch stays. The filter runs on the whole grid: the frame (and on shaped panels every point outside the inner outline, `visible_points`) stands at the frame's height, so a patch that joins the frame is no island and a hole that runs under the frame counts only its visible part. `colour_map` smooths the ideal heights the same way, and `palette.score` puts the Delta E of the smoothed heights (over the visible points) into the plan: report, preview and notes describe the print that is made, while `analyze` shows the plan before smoothing. A note says when no point of the picture reaches the last filament any more. A `--min-patch` as large as the picture is an error (scikit-image would return -1 everywhere); one at or below one grid point turns the filter off, and the report says so. The white outlines on that print sit on both sides of high steps (probably the white layers in their walls): this filter does not touch them. `--min-patch` with a mono print is a usage error. The frame is the whole stack (`color_range[1]`): it shows the last colour of the path (the darkest lit from behind, the top filament in room light).
- **Focus (`--focus`, colour only).** The subject of the photo gets the colours first. The map is in photo space (a mask image stretched to the photo, a box `X,Y,W,H` in photo pixels, or `centre`: a Gaussian with a sigma of a quarter of the picture, around the middle of the picture, not of the photo) and follows the photo through `image.window` (the user's crop, then the panel's aspect) to the grid (`focus.on_grid`). `palette.plan(..., focus, floor)` gives `Fitter` the weights floor + (1 − floor) × map (`--focus-floor`, 0.1 by default, at least 0.01), and `Fitter` samples its 3000 pixels in proportion to them, with repeats: without repeats a small subject runs out of pixels and weighs less than its weight. Without a map the sample is drawn exactly as before (no `p`: NumPy draws another sample with a `p`, even an even one), so plans without `--focus` do not change. The k-means starts and `photo_colours` come from the weighted sample too. The points where the map is at least `focus.SUBJECT` (0.5) are the subject: `palette.score(..., subject)` gives `Fit.focus_de`, `report.md` and `plan.json` (`subject_delta_e`, and `focus` with the share of the picture) show it, `colour_notes` says when the subject is still further from the photo than the whole picture, `preview.png` outlines it (`render.outlined`), and `focus.png` holds the map. On shaped panels the points under the frame are never the subject (they keep the floor weight, as without `--focus`, and the preview draws no outline there). A map with no subject in the picture (a black mask, a box outside the photo, cropped away, hidden by the frame or smaller than a grid point) is an error. A mask whose proportions differ from the photo's (upright) by more than 2 % gets a note: it is stretched to the photo. `analyze --focus` maps the whole photo, as its plan does, so `centre` there is the middle of the photo, not of the panel. With mono it is a usage error. The ideal colours still depend on the photo alone: the map is the user's description of the photo. **Regions (`feature/focus-regions`).** With `--focus` the heights are also smoothed per region. On the subject (`ColourMap.subject`, on the full grid for `remove_specks`) `forge.smooth_heights` replaces the 3 × 3 median with a grey opening and then a grey closing (`scipy.ndimage`) with a square of `ceil(MIN_WIDTH / pitch)` points (`MIN_WIDTH` = 0.4 mm, about one nozzle line; at a pitch of 0.4 mm or more the square is one point and the subject keeps `assign`'s heights): they remove only parts narrower than that and keep the corners and small spots that the median removes. `remove_specks(..., subject=, subject_cells=)` decides part by part (`_regional_opening`, a threshold decomposition with `scipy.ndimage.label` per layer, then the same on the negated heights for the holes): an island or a hole that touches the subject needs `Job.subject_patch` points (`--min-patch-subject`, at most `--min-patch`, a usage error above it; when not given, 0.64 mm² or a smaller `--min-patch`), one wholly outside it `--min-patch`. Being large enough is inherited by the larger part one layer down, so this is an opening, it equals scikit-image's `area_opening` when no point is marked (a test checks it), and it needs no special case at the seam (an earlier version joined two filtered grids with `np.where` and could leave a background hole under `--min-patch` there). It is also about 14 times faster than scikit-image at 120 mm (0.12 s); the path without `--focus` still uses scikit-image, so plans stay byte-identical. Before `assign`, `palette.smooth_background` smooths the target with a bilateral filter in CIELAB (one scale on every channel, colour sigma `SMOOTH_DE` = 10, spatial sigma `--smooth-background` / pitch points, 0.4 mm by default, at most `MAX_SMOOTH` = 2 mm because the time grows with its square) and blends it by 1 − the map. scikit-image divides the colour distance by the number of channels, so it gets `SMOOTH_DE / 3`; the first version passed 5 and so smoothed at 15, which erased the gables of the ruins. With negative values scikit-image shifts the image but builds its weight table for the old range, so we shift CIELAB to positive values ourselves. The owner chose 10 on 2026-11-04 (5 keeps every edge but removes few specks, 15 is calmest but loses the gables). The blend by 1 − the map means a box or mask subject keeps the photo and a soft map (`centre`, `subject`) is smoothed a little where it is below 1. Only the heights use it: the fit (filaments, change heights) and `palette.score` still use the photo, so a `--focus` plan's filaments do not change and the Delta E stays honest. Without `--focus` nothing of this runs: `smooth_heights` is the old median and `remove_specks` gets the old four arguments (the spy in `test_colour_map_has_no_specks` relies on it), and plans are byte-identical. Measured on Machu Picchu at 120 mm, 5 colours, `--focus subject` (spike in `out/focus-regions-spike/`, git-ignored): subject Delta E 10.38 → 10.06, whole picture 10.80 → 10.77, background patches −49 % (10,515 → 5,351), 1-3 mm² islands and holes in the background −45 % (1,824 → 1,011), PrusaSlicer's estimate 4 h 26 min → 3 h 58 min. Dropping the median on the subject with no filter gave 9.9, but 7.7 % of the subject's points were then in parts narrower than 0.4 mm, which do not print. Local contrast (sharpening) on the subject was measured worse (+0.36, a noisier face) and left out. Whether 0.64 mm² patches print clean is not measured yet: the next test print decides (else the default becomes 1 mm²). `--min-patch-subject` and `--smooth-background` are `make` options that go with `--focus` (usage errors otherwise, and with mono); `analyze` shows the plan before smoothing and does not take them. `plan.json` `focus` has `subject_min_patch_mm2`, `subject_min_patch_points`, `subject_min_width_mm` and `smooth_background_mm`; `report.md` says what each region keeps and which option set the subject's limit (`forge.speck_lines`), and the note about a last filament that no point reaches also names `--smooth-background 0`. `--focus subject` finds the map by itself (`vision.py`): three segmentation models (u2net_human_seg, MODNet at a short side of 512, IS-Net general use) run once each on the whole photo and the map is their mean, so a point is the subject (0.5) when two of three agree. Each model alone failed somewhere on the owner's photos (a raised hand, two shoes, a rock touching a hand, a rope fence; MODNet at 1024 px also marked a mountain peak), but the mean found the people on 10 of the 11 photos with people (on the eleventh a face cut by the frame was half marked) and nothing in the open landscapes. `vision.drop_small` drops the parts (where the mean is at least 0.1) whose core covers less than `focus.MIN_FOUND` (0.2 %) of the photo: false parts were at most 0.07 %, real ones at least 0.6 %. Without people the models mark the main object (a plate of fruit), so the keyword is `subject`, not `person`; an open landscape gives nothing and `check_subject` says so. No min-max stretch (rembg does one): it would turn "nothing" into a full mask. BiRefNet lite was the first choice, but its ONNX export decomposes deformable convolutions into 784 MB tensors and does not run in 8 GB. The models run on the CPU in about a second; `--device auto` uses CUDA when the `vision-gpu` extra offers it (and `preload_dlls()` loads the nvidia wheels' libraries), and `plan.json` `focus.found` and `report.md` name the models and the device. The spike is in `out/vision-spike/results.md` (git-ignored). This is the subject-emphasis plan (`out/subject-emphasis-analysis.md`, git-ignored): after regional smoothing (above) come faces and depth.

## Frames

- **Panel frame:** u along the width (left to right as the viewer sees it), v up, w through the thickness (0 on the flat face).
- **Standing (flat):** u → x, v → z, w → +y. The viewer of the flat face stands at −y.
- **Curved:** bent around the z axis, the flat face on the outer radius, the middle facing −y. The width is the arc length on the flat face.
- **Lying (colour and shaped panels):** u → x, v → y, w → z. Seen from below (the bed face), left and right swap: with `view="flat"` all volumes are mirrored in x. With `view="relief"` (always for light from the front) nothing is mirrored: PrusaSlicer's top view shows the picture as the viewer sees it.
- **Cylinder:** like curved, closed: u from −π r to π r around the z axis.
- `thickness_map` returns the grid as the viewer sees it (row 0 at the top); `panel()` turns it into mesh order (row 0 at the bottom; for standing panels the columns are swapped for `view="relief"`, while lying panels are mirrored in x for `view="flat"` and left as they are for `view="relief"`).
- `Job.view` is the user's choice, None by default; the code reads `Job.face`, a property that resolves it from the light: `"relief"` for `light="front"`, else `"flat"`. It is a property, not a value set once in `__post_init__`, so that `replace(job, light=...)` follows the light. `Job.front_lit` and `Job.part_name` hold the front-light wording in one place.

## 3MF and PrusaSlicer notes

- We write the 3MF ourselves (numpy → XML). `Metadata/Slic3r_PE_model.config` gives each object its volumes (triangle ranges) and per-object settings. PrusaSlicer joins overlapping volumes of one object when it slices (checked by hand with two crossing boxes: the filament matches the union).
- Per-object settings keep the system presets clean (the one exception is the filament colour, below): the project shows "Original Prusa MK4 Input Shaper 0.4 nozzle", "0.10mm FAST DETAIL @MK4IS 0.4", "Prusament PETG @PGIS", plus the object's own perimeters, 100 % infill, rear seam and 8 mm brim.
- The CLI crashes on `--export-3mf` without a display. So `make` slices once to text G-code, copies the `; prusaslicer_config` block into `Metadata/Slic3r_PE.config` and sets `binary_gcode` back to the printer's value. `--slice` slices the project a second time to `.bgcode`. The auto-support probe and the "project carries the printer" check live in `tests/test_slicer.py`, not in every run.
- Every slice gets a temporary `--datadir` with the vendor bundle and a `PrusaSlicer.ini` that installs the printer model and the variant (nozzle) of the printer preset in use, so results do not depend on the user's PrusaSlicer settings. PrusaSlicer silently takes other presets when the model or variant is missing, so `slicer.check_presets` compares the G-code's preset names with the asked ones and fails loudly.
- 100 % infill needs `fill_pattern = rectilinear`: the presets' default pattern refuses 100 %.
- M600 entries need `bed_idx="0"` (PrusaSlicer 2.9), or the GUI silently drops them.
- The filament presets in the printer table all have `filament_colour = #FF8000` (orange; other Prusament presets in the bundle differ). `slice_project` passes `--filament-colour` to the first slice with `forge.first_colour`: the colour plan's first filament, or for white prints Signal White (`palette.white()`, from the catalog) in PETG and plain white in PLA. So the project and its G-code start with the filament you really load; the preset name does not change, but PrusaSlicer's GUI shows the filament preset as modified. Accessories keep the preset's colour. Without PrusaSlicer the 3MF has no configuration, so plan.json's `printer.filament_colour` is null.
- `load_filaments` accepts only `#RRGGBB` (or `RRGGBB`) and writes it as `#RRGGBB`: the same string goes to the preview, the M600 list and PrusaSlicer.
- Headless slicing makes no G-code thumbnail for the printer's screen. The 3MF has our own `Metadata/thumbnail.png`.

## Git

- **Always** use a feature branch (`feature/<topic>`, from an up-to-date `main`) for every change, small fixes and documentation included. Never commit to `main` directly.
